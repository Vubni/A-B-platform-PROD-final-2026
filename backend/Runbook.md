# Runbook — LOTTY A/B Platform

Операционная документация: запуск и проверка, наблюдаемость, логи, поведение при росте нагрузки и данных.

## Запуск и проверка (B1)

Инструкция для воспроизведения запуска и первичной проверки системы (в т.ч. для жюри). Все команды выполняются **из корня репозитория**, если не указано иное.

### Предусловия

| Требование | Описание |
|------------|----------|
| Docker, Docker Compose | Приложение запускается командой `docker compose up -d`. |
| Порты | Сервисы слушают только порт **80**; общение между контейнерами — через docker-сеть. |

### Переменные окружения

Значения берутся из окружения; при отсутствии — из дефолтов в `backend/config.py`. В `docker-compose.yml` для backend заданы часть переменных; остальные — дефолты из кода.

| Env | Дефолт | Назначение |
|-----|--------|------------|
| `DB_HOST` | `postgres` | Хост PostgreSQL |
| `DB_USER` | `user` | Пользователь БД |
| `DB_PASSWORD` | `prod_secret` | Пароль БД |
| `DB_NAME` | `prod` | Имя базы данных |
| `RANDOM_SECRET` | `AJd27GqoS#gvxp@V` | Секрет для подписи JWT |
| `SEED_DEMO_USERS` | `1` | При `1` при старте создаются тестовые пользователи, флаг `test_feature_flag`, типы событий `demo_*`, метрики, группа аппруверов |

Полный список переменных и описание — в `backend/README.md`, раздел «Переменные конфигурации».

Для запуска тестов локально задают `API_BASE_URL=http://localhost:80` (или порт, на котором слушает backend).

### Точные команды старта

**Вариант 1 — Docker (рекомендуется для проверки):**

```bash
docker compose up -d
```

API доступен по адресу: `http://localhost:80`. Логи backend — volume `backend_logs` или вывод контейнера.

**Вариант 2 — Локально (без Docker):**

```bash
cd backend
pip install -r requirements.txt
python server.py
```

Перед запуском нужна доступная БД PostgreSQL 14+ (схема из `docker/postgres/01-init.sql` и `schema/`). Переменные `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` задать в окружении или `.env`.

### Команды проверки и ожидаемый вывод

Выполнять после старта (для Docker — дождаться готовности, до 180 секунд).

**1. Проверка доступности (liveness):**

```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:80/health
```

**Ожидаемый вывод:** `200` (в теле при полном выводе может быть `{"status":"ok"}` или аналог).

**2. Проверка готовности (readiness, БД инициализирована):**

```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:80/ready
```

**Ожидаемый вывод:** `200` — сервис готов к приёму запросов. До инициализации БД может быть `503`; повторять до 200 в течение 180 с.

**3. Проверка метрик (observability):**

```bash
curl -s http://localhost:80/metrics | head -30
```

**Ожидаемый вывод:** текст в формате Prometheus, например строки вида `# HELP http_requests_total ...`, `http_requests_total{...} 0` и т.п.

**4. Минимальный сквозной сценарий (опционально):**

Получение токена и запрос списка флагов (после готовности `/ready` и при включённом сиде демо-данных):

```bash
curl -s -X POST http://localhost:80/api/v1/auth \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@test.com","password":"admin123"}'
```

**Ожидаемый вывод:** JSON с полем `token` (JWT). Код ответа **200**. При неверном пароле — **401**.

Дальнейшие сценарии (decide → events → report), тестовые данные и ожидаемые коды — в **`backend/docs/reviewer-test-guide.md`** и **`backend/docs/demo-scenarios.md`**.

| Шаг | Действие | Ожидаемый результат |
|-----|-----------|----------------------|
| 1 | `docker compose up -d` | Контейнеры запущены |
| 2 | `curl -s -o /dev/null -w "%{http_code}" http://localhost:80/ready` | `200` (в течение 180 с) |
| 3 | `curl -s -o /dev/null -w "%{http_code}" http://localhost:80/health` | `200` |
| 4 | `curl -s http://localhost:80/metrics` | Строки Prometheus-метрик |

После шага 2 система готова к приёму запросов; тестовые пользователи и флаг `test_feature_flag` доступны при `SEED_DEMO_USERS=1` (значение по умолчанию в docker-compose).

## Наблюдаемость и логи (B9-4)

### Формат логов

Логи выводятся в **структурированном виде**: одна строка — один JSON-объект с фиксированным набором полей. Это обеспечивает стабильный формат для парсинга (ELK, Loki, CloudWatch и т.п.) и удобный поиск по полям.

**Поля записи лога:**

| Поле        | Тип    | Описание |
|-------------|--------|----------|
| `timestamp` | string | Время события в UTC, ISO 8601: `YYYY-MM-DDTHH:MM:SS.sssZ` |
| `level`     | string | Уровень: `DEBUG`, `INFO`, `WARNING`, `ERROR` |
| `logger`    | string | Имя логгера (например, `backend`) |
| `message`   | string | Текст сообщения |
| `module`    | string | Имя модуля (файла) |
| `funcName`  | string | Имя функции |
| `lineno`    | number | Номер строки в коде |
| `exception` | string | Текст трассировки (только при логировании исключения) |

**Пример одной строки лога:**

```json
{"timestamp": "2026-02-20T12:00:00.123Z", "level": "INFO", "logger": "backend", "message": "LOTTY A/B Platform API started.", "module": "server", "funcName": "main", "lineno": 142}
```

**Пример с исключением:**

```json
{"timestamp": "2026-02-20T12:00:01.456Z", "level": "ERROR", "logger": "backend", "message": "Ошибка подключения к БД", "module": "database", "funcName": "connect", "lineno": 31, "exception": "Traceback (most recent call last):\n  ..."}
```

Файлы логов: `logs/all_logs.log` (все уровни), `logs/errors.log` (только ERROR). Ротация: 10 МБ на файл, до 3 резервных копий. Настройки — см. раздел «Логирование» в `backend/README.md`.

## Нагрузка и рост данных (B9-6)

Описание лимитов, масштабирования и поведения системы при росте нагрузки и объёма данных.

### Лимиты и ограничения

| Механизм | Переменная / место | Назначение |
|----------|--------------------|------------|
| Активные эксперименты на субъекта | `MAX_ACTIVE_EXPERIMENTS_PER_SUBJECT` (по умолчанию 2) | Ограничение числа одновременных экспериментов на одного subject_id |
| Кулдаун повторного входа | `EXPERIMENT_COOLDOWN_SECONDS` (по умолчанию 7 суток) | Задержка перед повторным попаданием субъекта в эксперимент по тому же флагу |
| Привязка событий к решению | `EVENTS_DEPENDENCY_MAX_DELAY_DAYS` (по умолчанию 7) | События старше N дней не привязываются к decision |
| Один активный эксперимент на флаг | Ограничение в БД (unique index) | На один флаг одновременно только один эксперимент в статусе running/paused |
| Ротация логов | `LOG_MAX_BYTES`, `LOG_BACKUP_COUNT` в `config.py` | Ограничение объёма логов на диске |

При превышении лимитов система возвращает соответствующие HTTP-ошибки или не привязывает данные (события вне окна), что предотвращает неконтролируемый рост и перегрузку.

### Рост объёма данных

**Основные растущие таблицы:**

- `event_occurrences` — события (экспозиции, конверсии и т.д.)
- `decisions` — выданные решения (assignments)
- `experiment_guardrail_history`, `experiment_version_snapshots` — история по экспериментам

**Текущее поведение:**

- На таблицах `event_occurrences` и `decisions` есть индексы по `timestamp`/`created_at`, что позволяет эффективно выбирать данные за период (отчёты, очистка старых данных).
- Отчёты и выборки ограничиваются диапазоном дат (`start`/`end`), что ограничивает объём обрабатываемых строк при росте истории.

**Рекомендации при дальнейшем росте:**

1. **Партиционирование (партиции по времени):**  
   Для `event_occurrences` и при необходимости для `decisions` — партиционирование по `timestamp`/`created_at` (например, по месяцам). Это ускоряет запросы по периоду и упрощает вынос/архивацию старых партиций.

2. **Архивация и очистка:**  
   Периодическое удаление или перенос в холодное хранилище записей старше N месяцев (с учётом `EVENTS_DEPENDENCY_MAX_DELAY_DAYS` и требований к отчётам). Можно реализовать фоновой задачей или cron-скриптом.

3. **Мониторинг размера таблиц:**  
   Отслеживать размер таблиц (например, `pg_total_relation_size`) и латентность тяжёлых запросов (отчёты, агрегации) — при росте планировать партиционирование и индексы.

### Масштабирование

- **Горизонтальное масштабирование backend:**  
  Несколько экземпляров приложения за балансировщиком нагрузки (без состояния в памяти). Достаточно задать общую БД и (при необходимости) общий секрет JWT (`RANDOM_SECRET`).

- **База данных:**  
  Увеличение ресурсов (CPU/RAM) и пула соединений (connection pool) при росте RPS. При очень высокой нагрузке — чтение реплик для отчётов и аналитики, запись в primary.

- **Kafka (реализовано):**  
  В проекте подключена Kafka (сервис в `docker-compose`, топик `lotty-events`). При `EVENTS_USE_KAFKA=true` и заданном `KAFKA_BOOTSTRAP_SERVERS` приём событий `POST /api/v1/events` пишет батчи в топик и возвращает **202** (события в очереди); in-process consumer читает топик и вызывает ту же логику записи в БД (`process_events_batch`) с идемпотентностью по `event_id`. По умолчанию `EVENTS_USE_KAFKA=false` — поведение синхронное. Переменные: `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_EVENTS_TOPIC` (по умолчанию `lotty-events`), `EVENTS_USE_KAFKA`.

### Краткое резюме поведения при росте

| Аспект | Поведение |
|--------|-----------|
| Лимиты | Жёсткие лимиты на эксперименты на субъекта, кулдаун, окно привязки событий; при превышении — предсказуемые ответы API. |
| Данные | Индексы по времени; отчёты по диапазону дат; при росте — партиционирование и архивация. |
| Масштабирование | Несколько инстансов backend за LB; масштабирование БД и пула соединений. |
| Очереди | По умолчанию синхронная обработка; при `EVENTS_USE_KAFKA=true` — приём событий через Kafka, consumer в процессе backend. |

Детали конфигурации — в `backend/README.md` и переменных окружения (`config.py`).

## Проверка guardrails (B5-3, B5-4)

Проверка правил guardrail **не выполняется по расписанию (cron)**, а вызывается **при обработке каждого батча событий** `POST /api/v1/events`: после принятия и записи событий по затронутым `decision_id` вызывается `check_guardrails_for_decisions`. Для каждого эксперимента, у которого есть решения в этом батче, пересчитываются guardrail-метрики за окно наблюдения (`window_seconds`); при превышении порога выполняется действие (pause или rollback_to_control) и запись в `experiment_guardrail_history`. Таким образом, реакция на деградацию происходит в близком к real-time режиме по мере поступления данных.

## База данных и триггеры

Схема БД и триггеры определены в `docker/postgres/01-init.sql` и файлах в `docker/postgres/schema/`. Триггеры используют синтаксис **`EXECUTE FUNCTION`**, который корректен в **PostgreSQL 14+**. Для окружений на PostgreSQL 11–13 в триггерах нужно заменить `EXECUTE FUNCTION` на `EXECUTE PROCEDURE`. Рекомендуемая минимальная версия для запуска по инструкции: **PostgreSQL 14**.

## Инженерная дисциплина (B10)

Используется **Ruff** (конфигурация в корневом `pyproject.toml`). Штатные команды выполняются **из корня репозитория**.

### Линтинг (B10-1)

Проверка кода линтером:

```bash
ruff check backend
```

Исправление автоисправляемых замечаний (опционально): `ruff check backend --fix` (из корня) или `ruff check . --fix` (из `backend`).

### Форматирование (B10-2)

Привести код к единому стилю (из корня): `ruff format backend`; из каталога `backend`: `ruff format .`

Проверка форматирования без изменений (для CI, из корня):

```bash
ruff format --check backend
```

### Установка Ruff

```bash
pip install ruff
# или из корня проекта с dev-зависимостями:
pip install -e ".[dev]"
```

В CI (см. `.github/workflows/lint.yml`) автоматически запускаются `ruff check backend` и `ruff format --check backend`.
